Foi feita busca no código por `@ProjectedPayload`, Querydsl web bindings, XSLT, Artemis, X.509, SSE de fragmentos e serviço JDBC de one-time token, além de testes de rotas e chamadas HTTP limitadas. Essa triagem é dependente da configuração atual; não elimina os alertas dos JARs. **Não foi comprovada vulnerabilidade crítica/alta explorável nos caminhos atuais**, mas o inventário do pacote permanece aberto e requer decisão de manutenção. Não há ignorefile global de CVEs.

Atualização de linha não foi forçada na integração: Spring Boot 3.4/Framework 6.2/Security 6.4/Data 3.4 têm correções de parte desses CVEs apenas no suporte Enterprise, enquanto migrar para Boot 3.5 ou 4 implica nova combinação de Security, Data, Hibernate e springdoc. Uma migração dessas exige matriz de compatibilidade e reexecução integral; alterar só um BOM às cegas poderia quebrar autenticação ou persistência. A aprovação de código depende de aceite técnico documentado dos riscos residuais ou de um PR de atualização testado.

O frontend teve zero CVEs na imagem final e `npm audit --omit=dev` zerado. `npm audit` completo apontou **16 avisos moderados** no ecossistema ESLint/minimatch de desenvolvimento, sem alto/crítico. Não estão no runner standalone. O `npm audit fix --force` sugeriu versões incompatíveis com a configuração atual; planejar atualização coordenada de ferramentas e manter entrada não confiável fora do lint.
